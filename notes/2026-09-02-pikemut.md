# Mutable-buffer PikeVM experiment (2026-09-02) — negative result

Profiling (notes/2026-09-02-benchmark.md follow-up) showed `find_all` spends
**~78% of its time in malloc/free + refcount + memcpy**, not matching: the
functional `Pike` rebuilds immutable `List`s on every NFA step and re-seeds a
fresh slot array at every input position. This experiment tested whether a
mutable, buffer-reusing PikeVM closes that gap.

## What was built

`package/PikeMut.roc` — `find_all_mut`, computing all matches in one call with
every working structure a preallocated `var` reused for the whole scan:

- two thread queues (clist/nlist): a `pc` list + a **flat slot arena**
  (`slot[i*ns .. i*ns+ns)`, no per-thread `List`s / nested refcounts);
- **generation-counter** dedup sets (`seen[pc] == gen`), cleared by `gen += 1`;
- a reused DFS work-stack; the epsilon-closure inlined (no helper) to keep
  buffers uniquely owned;
- buffers pre-sized to the program length, reused **across matches** as well as
  positions (only the result slot array is allocated per match).

This mirrors how Rust's `regex-automata` PikeVM works (sparse sets + a flat slot
arena allocated once).

## Correctness

Same leftmost-first + D14 empty-match semantics as `Regex.all_caps`. Match
counts equal Rust's on all 9 benchmark patterns; the earlier per-match
`captures_from` variant passed the full 860/860 differential; empty-match cases
(`a*`, `(a*)*`, `a|`) correct.

## Result — SLOWER, so not adopted

16 KiB haystack, ns/iter for `find_all`, functional `Pike` vs `find_all_mut`:

```
pattern       Pike_ns   mut_ns    ratio
literal       6974000   10603100  1.52x slower
teddy_alt    29784750   77383100  2.60x
class_plus   10277950   24121200  2.35x
bounded_num   6488800   12299900  1.90x
word_bound   25823000   42229000  1.64x
two_words    12403700   22115300  1.78x
caps_email   14954350   41389050  2.77x
uni_letters  10298950   19154050  1.86x
dotstar_lit  13905800   27118100  1.95x
```

1.5–2.8× slower across the board, and it degrades further at larger haystacks.

## Why — corrected profile (the interesting part)

The in-place mutation **works**. `List.set(x,i,v) ?? x` mutates when the list's
refcount is 1 and copies otherwise (the whole heuristic); on a reused 2000-elem
`var`, 3,000,000 sets run in ~1 ms. Profiling `find_all_mut` itself (once the
right variant was measured — an earlier "~80% malloc" figure was the *per-match*
`captures_from`, which reallocates per match) shows the buffers stay uniquely
owned: **refcount traffic ~0%, allocation ~24%, matching code ~68%**. So the
rewrite did what it set out to do — it removed the allocation.

The subtlety is that "allocation is the bottleneck" was itself a *speed-build*
statement. Measuring both engines under each backend, ns/`find_all` over the
same 16 KiB haystack (`[A-Za-z]+`):

```
                 alloc%   engine%   time/call
functional (speed)  78%      22%      10 ms      <- shipped; LLVM optimises the
                                                    compute away, leaving alloc
mutable    (speed)   —        —       24 ms      <- SLOWER; see below
functional (dev)    18%      75%      79 ms
mutable    (dev)    24%      68%      61 ms      <- FASTER than functional
```

Two things follow. (1) Functional Pike is 78% allocation only *after* LLVM
shrinks its compute; under `dev` (no optimisation) compute dominates and
allocation is a minor 18%. (2) Under `dev`, where neither engine's compute is
optimised, the mutable version is **~20% faster** — exactly what removing the
allocation should buy. It is only the **LLVM (`--opt=speed`) backend** that
reverses this: it optimises functional Pike's small-list compute dramatically
(10 ms) but handles the large `find_all_mut` far worse (24 ms) — and the same
function makes the LLVM build itself blow up (see below). So the allocation win
is real; it just can't pay off in the shipped build because of how the LLVM
backend treats this one big function.

### Compile blowup (`--opt=speed`)

`find_all_mut` (one ~250-line function, six nested `while`s) builds in **~1 s on
`--opt=dev` but takes minutes on `--opt=speed`** (killed at 3 min in a tiny
harness; a larger app did finish once, ~2 min). The Roc frontend runs in both
and finishes in ~1 s (dev proves it), so the cost is in the speed/LLVM codegen
path. Worth an upstream repro alongside the tail-call and in-place-mutation
threads — the pattern is "a single large mutable function is pathological for
the LLVM backend, in both compile time and generated-code quality."

Getting to a correct version also surfaced several sharp edges, each of which
corrupted the heap until worked around:

- passing a still-live buffer into a `close` helper → clone every call (malloc
  went *up* to 69%); fixed by inlining;
- reused nested `List(List(U64))` slot buffers → double-free; fixed by the flat
  arena;
- `List.append` reallocating an aliased buffer mid-scan → double-free; fixed by
  pre-sizing and using `List.set` only;
- `List.sublist` for the match result possibly sharing the arena's backing;
  fixed by copying out element-by-element.

## Takeaway

Corrected from the first pass: the allocation win is **real** — the mutable
buffers mutate in place (rc≈0%) and cut allocation to ~24%. Under a backend that
doesn't over-optimise the alternative (`dev`), the mutable engine is already
faster. What blocks it from shipping is the **LLVM backend**: it both blows up
compiling `find_all_mut` and generates slower code for it than for functional
Pike's small-list style, so under `--opt=speed` the mutable version is ~2× slower
despite doing less allocation.

So this is not "mutation doesn't help in Roc" — it's "the LLVM backend can't yet
turn this mutable engine into fast code." Two upstream-worthy items:

1. LLVM-backend compile blowup on one large mutable function (dev 1 s, speed
   minutes) — the concrete new finding here.
2. Poorer LLVM codegen for the big-function/flat-buffer style vs many small
   immutable-`List` calls.

Both sit next to the tail-call issue (`upstream/2026-09-02-llvm-tco-match-loop/`)
as backend limitations standing between this engine and Rust-class throughput.
The functional `Pike` remains the shipped engine; `PikeMut.roc` is kept dormant
as the reproduction artifact — and as evidence the allocation reduction works
the moment the backend can compile it well.
