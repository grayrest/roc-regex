# Mutable-buffer PikeVM experiment (2026-09-02) — negative result

Profiling (notes/2026-09-02-benchmark.md follow-up) showed `find_all` spends
**~78% of its time in malloc/free + refcount + memcpy**, not matching: the
functional `Pike` rebuilds immutable `List`s on every NFA step and re-seeds a
fresh slot array at every input position. This experiment tested whether a
mutable, buffer-reusing PikeVM closes that gap.

## What was built

`package/PikeMut.roc` — `find_all_mut`, computing all matches in one call with
every working structure a preallocated `var` reused for the whole scan:

- two thread queues (clist/nlist): a `pc` list + a **flat slot arena**
  (`slot[i*ns .. i*ns+ns)`, no per-thread `List`s / nested refcounts);
- **generation-counter** dedup sets (`seen[pc] == gen`), cleared by `gen += 1`;
- a reused DFS work-stack; the epsilon-closure inlined (no helper) to keep
  buffers uniquely owned;
- buffers pre-sized to the program length, reused **across matches** as well as
  positions (only the result slot array is allocated per match).

This mirrors how Rust's `regex-automata` PikeVM works (sparse sets + a flat slot
arena allocated once).

## Correctness

Same leftmost-first + D14 empty-match semantics as `Regex.all_caps`. Match
counts equal Rust's on all 9 benchmark patterns; the earlier per-match
`captures_from` variant passed the full 860/860 differential; empty-match cases
(`a*`, `(a*)*`, `a|`) correct.

## Result — SLOWER, so not adopted

16 KiB haystack, ns/iter for `find_all`, functional `Pike` vs `find_all_mut`:

1.5–2.8× slower across the board, and it degrades further at larger haystacks.

## Why it's slower — what's actually defensible

Only **same-backend** comparisons are valid here (correcting the earlier draft).
The dev and speed backends are not two speeds of the same pipeline: the speed
path additionally runs Roc's folding, inlining, in-place-mutation analysis and
type specialization before emitting code, so dev-backend *relative* performance
and dev-backend allocation profiles **do not predict** the shipped build. The
numbers I collected under `--opt=dev` (a ~24%-alloc profile, mutable ~20% faster
than Pike) are therefore discarded as non-transferable — they do not support any
claim about the speed build, including "the allocation win is real."

What stands, both measured under the shipped `--opt=speed` backend on the same
16 KiB `[A-Za-z]+` haystack:

- functional Pike: 10 ms/`find_all`;
- mutable `find_all_mut`: 24 ms/`find_all` — **~2.4× slower**.

I could **not** profile `find_all_mut` under `--opt=speed` (its speed build is
pathologically slow, below), so I cannot say where that 24 ms goes. The earlier
"78% allocation" figure is a valid *speed-build profile of functional Pike*; it
says nothing about the mutable version. So: the mutable engine is correct and,
in the shipped build, slower — and the reason is not established.

### Compile blowup is in Roc's optimizer, not LLVM

`find_all_mut` (one ~250-line function, six nested `while`s) builds in **~1 s on
`--opt=dev` but takes minutes on `--opt=speed`**. This is **not** LLVM: LLVM
scales roughly linearly in code size and is only a couple of seconds on code
this size. The extra speed-path work is Roc's own optimization passes
(folding / inlining / in-place-mutation / specialization), and the blowup is
there — most likely because a **single giant mutable function is unlike anything
in normal Roc code**, so those passes aren't tuned for it. (This is the compiler
maintainer's read, and it fits: dev, which skips those passes, is instant.)
That's the one clean, novel upstream item from this experiment.

Getting to a correct version also surfaced several sharp edges, each of which
corrupted the heap until worked around:

- passing a still-live buffer into a `close` helper → clone every call (malloc
  went *up* to 69%); fixed by inlining;
- reused nested `List(List(U64))` slot buffers → double-free; fixed by the flat
  arena;
- `List.append` reallocating an aliased buffer mid-scan → double-free; fixed by
  pre-sizing and using `List.set` only;
- `List.sublist` for the match result possibly sharing the arena's backing;
  fixed by copying out element-by-element.

## Takeaway (after two wrong drafts)

What is actually established:

- `find_all_mut` is correct (match counts = Rust on all 9 bench patterns; the
  `captures_from` variant passed 860/860; empty-match cases right).
- Under the shipped `--opt=speed` backend it is **~2.4× slower** than functional
  `Pike` (24 vs 10 ms/`find_all` @16 KiB).
- Its `--opt=speed` build blows up in **Roc's optimization passes** (not LLVM),
  triggered by being one giant mutable function — atypical Roc code the
  mid-end isn't tuned for.

What is **not** established, and where I over-reached before:

- Whether the mutable design reduces allocation *in the shipped build*. My only
  allocation profile of it was under `dev`, which skips the relevant passes, so
  it doesn't transfer. Unknown.
- Why it's slower at speed. No speed-build profile was obtainable.
- Any "it would win if the backend cooperated" claim — that rested entirely on
  non-transferable dev numbers.

Practical reading: the single-giant-`var`-function shape is itself the problem
— it breaks Roc's optimizer and isn't idiomatic. A real mutable engine would
have to be decomposed into normal-sized functions, which reintroduces the
question of keeping buffers uniquely owned (rc 1) across call boundaries so
`List.set` mutates rather than copies. Whether that can be made both fast and
in-place under `--opt=speed` is unresolved and would need Roc-team input.

The one clean upstream item is the optimizer compile blowup on a large mutable
function. The functional `Pike` remains the shipped engine; `PikeMut.roc` is
kept dormant purely as that reproduction artifact.
