## Why

Rust's `regex` compiles patterns at runtime. Getting a pattern compiled ahead of
time needs a proc macro, a build script, or a separate serialization mode —
`regex-automata` ships `dfa::dense::DFA::to_bytes_little_endian` precisely
because there is no way to get a table into a binary otherwise.

Roc evaluates pure expressions with compile-time-known arguments during the
build and stores the result in the executable. Measured: a `List(U64)` whose
construction costs 10⁹ operations builds in 4.9 s and runs in 0.006 s, and an
invalid input reaching a `crash` during that evaluation fails the build with the
crash message. So a regex library written as ordinary pure Roc gets ahead-of-time
compilation and compile-time pattern validation with no macro, no build step and
no second mode — the same `compile` function serves a literal pattern and a
pattern read from `argv`, and only the literal one gets folded.

That is the whole idea. Everything below is what it costs.

## The shape

Rust's pipeline, minus what purity forbids, plus what folding makes affordable.

    pattern → AST → HIR → Thompson NFA → { PikeVM, dense DFA }

Three things differ from the original, all forced:

1. **No lazy DFA.** `regex-automata`'s hybrid engine mutates a state cache during
   the search. A pure function cannot. It is replaced by *eager* determinization
   under a byte budget — which is affordable exactly because the folded case pays
   for it at build time, and which is why laziness existed in the first place.
2. **No SIMD.** `src/builtins/simd.zig` is internal to the compiler's builtins;
   there is no user-facing vector type. Every prefilter is a scalar loop, so the
   prefilter is an optimization here rather than the load-bearing structure it is
   in Rust.
3. **No unchecked indexing.** The inner loop is `List.get` returning
   `Try(U8, [OutOfBounds])`. This port will not approach Rust's throughput and
   should not be sold as if it might.

## What is measured, and at what scale

The full table is in the probe log. The five results the plan rests on:

| claim | measurement |
|---|---|
| compile-time evaluation is real, unbudgeted | 2×10⁹ iterations: build 9.91 s, run 0.172 s |
| heap values fold and reach runtime | 100-elem `List(U64)`, 10⁹ ops: build 4.93 s, run 0.006 s |
| folds are cached and parallel | cold 1.24 s / warm 0.22 s; three folds 4.72 s user, 1.74 s wall |
| folded lists are packed at element width | `U32` 1M elems → 4 005 520 bytes of binary, 4.00 b/elem |
| folding stops at the first runtime argument | `f("lit", runtime)`: build 0.29 s, **run 0.62 s** |

The last row is the one that shaped the API, and it was found by correcting a
probe that had appeared to show the opposite.

**Not measured, and it gates everything:** the state count of a determinized
Unicode pattern. M0 measures it before any Roc is written.

## Stop rules

1. **M0's number kills or keeps the DFA.** If the median realistic Unicode
   pattern determinizes past **1 MB of combined forward+reverse table**, eager
   determinization is not the headline feature. The DFA demotes to an opt-in
   accelerator for simple patterns, the PikeVM becomes the default path, and the
   project's claim changes from "AOT-compiled regex" to "regex with compile-time
   validation". Decide that at M0, not at M3.
2. **The fold must not go superlinear in pattern size.** M1 measures fold time
   and binary size for a realistic ASCII pattern. If a single ordinary pattern
   costs more than ~2 s of build time, or if build time grows faster than the
   artifact, stop and re-plan — everything here assumes the fold is a cost you
   pay once per pattern, not a cost that compounds.
3. **Compilation and searching never appear in the same call expression.** One
   runtime argument disables folding for everything inside that call. If the API
   ever grows a function taking both a pattern and a haystack, the feature is
   gone and the library is a slow runtime regex engine. This is a rule about the
   public surface, not an implementation detail.
4. **`Str` and `Iter` stay out of the inner loop.** `Str` because matching is
   byte work and conversion copies; `Iter` because each step allocates its `rest`
   closure. `Iter` belongs at the match level, never the byte level.
5. **The corpus stays two-path.** With a folding design, "it works" and "it works
   when compiled" are different claims. If the runtime path is dropped from the
   suite for build-time reasons, stop.

## Build order

### M0 — Gate measurement, in Rust, hours not days

A ~30-line program over `regex-automata`'s `dfa::dense::Builder`, building
forward and reverse DFAs for ~30 realistic patterns with Unicode enabled, and
printing `memory_usage()`, `alphabet_len()` and state counts. All five crates are
already vendored under `~/.cargo/registry`.

Output: the default byte budget for D10, and a verdict on stop rule 1. **No Roc
is written until this number exists.**

### M1 — ASCII vertical slice, end to end

Subset parser and error rendering, Thompson NFA with pattern IDs threaded,
PikeVM, and the full v1 API surface: `find`, `find_iter`, `captures`, `replace`,
`replace_all`, `split`. Passes `no-unicode.toml` and the ASCII-safe subset of the
corpus, on both paths.

Vertical rather than layered on purpose. Every decision here rests on the fold
behaving a particular way at *library* scale — an artifact built by a call chain
hundreds of functions deep, embedded in a binary, indexed at runtime — and that
has only been shown on toys. **Gate: measure fold time and binary size for a
realistic ASCII pattern.** A cliff shows up here, with an ASCII PikeVM to throw
away, or it shows up at M3 with a determinizer to throw away.

### M2 — Unicode Tier A

Table generator from UCD emitting packed string literals; pure decoders whose
input is a literal, so they fold unconditionally. HIR class expansion, class set
operations, simple case folding, UTF-8 automata (`range_trie`, the hardest 1 000
lines in the original). Full 858-case corpus.

### M3 — Determinizer and dense DFA

Byte equivalence classes, forward and reverse tables, the byte budget from D10,
silent downgrade to the PikeVM when it is exceeded. The differential fuzzing
campaign runs here, because determinization bugs are the kind that appear on
pattern #400 and not in a corpus written against someone else's implementation.

### M4 — Literal extraction and the prefilter seam

`hir/literal.rs`'s job, then `find_candidate : List(U8), U64, Prefilter -> Try(U64, [NoCandidate])`
with a scalar loop behind it. The seam matters more than the implementation: a
SIMD builtin later is a one-file substitution, and Teddy — if user-facing vector
types ever land — slots in at the same interface.

## Decisions

### D1 — Runtime patterns are supported; one API, one code path

Rejected: compile-time-only, which makes "grep a user-supplied pattern"
inexpressible. Rejected: separate entry points for folded and runtime patterns,
which is the separate mode this project exists to avoid.

The consequence is that every engine must be safe to run at match time on
adversarial input, which is what forces D2's budget.

### D2 — PikeVM spine, eager dense DFA under a caller-supplied budget

The lazy DFA is impossible (purity). Full determinization at build time is its
replacement and is strictly better *for a folded pattern* — no cache, no
laziness, no per-search state.

Nothing in the language lets a function ask whether it is being folded, so the
budget cannot differ between build time and runtime. It is therefore an explicit
argument: `Regex.compile(pattern)` takes a conservative default,
`Regex.compile_with(pattern, { max_table_bytes })` for the folded case. The cost
of the choice is visible at the call site instead of hidden in a mode.

> **Amended 2026-09-01 by [the codepoint-alphabet studies](../notes/2026-09-01-codepoint-alphabet.md).**
> D2 survives, but **only over a codepoint alphabet**, and two of its claims were
> wrong.
>
> "Strictly better for a folded pattern — no cache, no laziness, no per-search
> state" was **false over bytes**: Unicode `\b` forces a quit set, whose
> search-time `Err(Quit)` on the first non-ASCII byte would have required a
> PikeVM and its NFA co-resident in every artifact. Over codepoints there is no
> quit set and the claim holds as written.
>
> The budget bounds **the wrong quantity**. `max_table_bytes` caps the artifact;
> the cost that actually bit was transient allocation during expansion, which is
> unbounded by it and which nothing frees (see D13). The budget must be checked
> **during expansion**, not against the finished table — see D14.
>
> The reviewers' objection that eager determinization is unaffordable was correct
> for the byte alphabet and does not survive the alphabet change: `\w{10,20}`
> falls from 10,229,144 bytes to **1,264**, and the largest table produced
> anywhere in the verification run was 1,856 bytes.

### D3 — Byte-oriented automaton, equivalence classes, `List(U8)` haystacks

As `regex-automata`: Unicode classes compile to UTF-8 automata, the 256-symbol
alphabet compresses to equivalence classes, the inner loop is one table lookup
per byte with no decoding. The standard objection — Unicode classes explode the
state count — is the objection folding answers.

`List(U8)` is the primary haystack and matches are byte offsets. `Str` input goes
through `Str.to_utf8`, which copies; the `Str` layer is documented as convenience
and the byte API as the real one.

> **REVERSED 2026-09-01 by [the codepoint-alphabet studies](../notes/2026-09-01-codepoint-alphabet.md).**
> The automaton is **codepoint-oriented**, not byte-oriented. This decision was
> wrong, and wrong in exactly the way it argued it was right: it claimed folding
> answers the state-explosion objection. Folding does not answer it — it relocates
> it. Measured, 99.1–99.7% of the states of a `\w`-family byte DFA are UTF-8
> byte-sequence bookkeeping, not pattern structure (`\w{10,20}`: 19,959 byte
> states against **59** codepoint states; 113 byte classes against **2** codepoint
> classes). No table encoding rescues the byte alphabet — sparse gets 3.8× at a
> 4.5× search cost, row deduplication saves 2% and is sometimes negative, stride
> padding is 11.7%.
>
> **The replacement.** Transitions are over codepoint equivalence classes,
> typically 3–8 per pattern. `Utf8Sequences` and `range_trie.rs` — about 1,600
> lines and the hardest code in the original — are **not needed at all**.
>
> **The lookup structure is part of the decision, not an implementation detail.**
> Measured: a two-level trie with a 128-entry direct ASCII fast path costs
> 1.96 ns/codepoint against the byte loop's 1.95 ns/byte — free, and faster in
> MB/s on non-ASCII because it iterates once per codepoint. A binary search over
> the packed range table costs 14.2 ns/codepoint, 3.4–7.3× slower. The packed
> range list is the right **storage** format and the wrong **lookup** path.
>
> **Undecodable bytes get an explicit `Invalid` symbol class** (chosen 2026-09-01
> over dropping byte mode, and over carrying two alphabets). Matching on
> arbitrary `List(U8)` is therefore defined rather than undefined. The cost is an
> 8th start configuration and a third look-behind value, because
> `WordUnicodeNegate`, `WordStartHalfUnicode` and `WordEndHalfUnicode` are
> defined not to match adjacent to undecodable bytes — **reasoned, not tested**;
> it is M1 work with a test.
>
> **What is given up:** patterns that address individual bytes. `(?-u:.)`,
> `(?-u:[^a])` and `regex::bytes` semantics — matching the single byte `0xC3`
> inside `"é"` — are not expressible and are deferred. ASCII-only `(?-u)`
> patterns keep their meaning and were verified. About 40 corpus cases sit in
> this gap.
>
> **Unchanged:** `List(U8)` remains the primary haystack type. Decoding reads
> from it; only the *pattern* loses byte granularity.

> **Amended 2026-09-02 by [the D6/D11 re-measurement](../notes/2026-09-02-d6-d11-remeasure.md) — the
> codepoint alphabet has no 256-symbol ceiling.** D3's win is Unicode *classes*
> collapsing to 3–8 symbols. A large **non-ASCII literal set** is the opposite
> case — one singleton class per distinct codepoint — and there the codepoint
> table is *larger* than the byte one: 1,000 CJK literals are 48,070,656 bytes
> over codepoints against 4,620,800 over bytes, and 5,000 project to 368 MB
> against 13.2 MB (**28×**). Neither is buildable under SR2. This is a
> large-literal-set problem rather than an alphabet problem and is out of v1
> scope, but the alphabet is not monotonically better and D3 should not be read
> as claiming it is.

### D4 — Unicode Tier A, tables as packed literals

`general_category` (6 717 lines in Rust), `case_folding_simple` (2 948),
`perl_word` (806). Not `property_bool` (12 095), scripts, age, or the break
properties — 25 k lines of table source for properties almost nobody writes.
Later tiers ship as separately-importable modules so a program that never writes
`\p{Greek}` never carries the table.

Tables ship as one packed string literal plus a pure decoder rather than as
generated range literals. The decoder's input is a literal, so the top-level
definition has no runtime inputs and folds unconditionally. Source stays small;
the expanded table lands in the ConstStore. This is the one place the port is
smaller than the original rather than larger.

`.` matches a codepoint by default, `(?-u)` makes it a byte. Empty matches do not
split a codepoint. An invalid-UTF-8 haystack is not an error; the automaton
simply will not match across the invalid bytes.

> **Amended 2026-09-01** by [the adversarial reviews](../notes/2026-09-01-adversarial-review.md) and
> [the codepoint-alphabet studies](../notes/2026-09-01-codepoint-alphabet.md).
>
> Three tables are missing. **`\s` is not in Tier A** and is not derivable from
> `general_category` — `White_Space` includes `Cc` characters — it needs
> `perl_space.rs`, 23 lines. **`\p{Letter}` / `\p{gc=Lu}` need name
> canonicalization**: `property_values.rs` (956) + `property_names.rs` (281),
> without which only `\pL`-style single letters work. `\d` is fine as planned,
> and **case folding is correct as planned** — the generated table already
> carries full equivalence classes, no orbit table needed.
>
> `utf8.rs` (592 lines) was a hard prerequisite of the byte alphabet and is
> **no longer needed** under D3's reversal.
>
> "`(?-u)` makes `.` a byte" and "an invalid-UTF-8 haystack is not an error" are
> both superseded by D3's `Invalid` symbol class: the haystack is still not an
> error, but the mechanism is a symbol class rather than byte-granular matching.
>
> The claim "this is the one place the port is smaller than the original" was
> made about unwritten code and should not have been stated. It happens to be
> true for a different reason — D3 deletes `range_trie.rs` and `utf8.rs`.

### D5 — Three-pass search

Forward DFA finds the match end; reverse anchored DFA finds the start; an
anchored PikeVM over that span alone fills capture slots. A DFA-backed regex
therefore carries two tables, and that is the first place a folded artifact gets
genuinely large.

Rejected: PikeVM-for-everything, which needs no reverse table but gives up the
throughput that motivates the DFA at all.

> **Amended 2026-09-01** by [the adversarial reviews](../notes/2026-09-01-adversarial-review.md) and
> [the codepoint-alphabet studies](../notes/2026-09-01-codepoint-alphabet.md). Three omissions, all
> confirmed real and now sized.
>
> **Start-state configuration is missing entirely.** There is no single start
> state. Over codepoints there are **8 configurations** (the crate's six, with
> `WordByte` split into ASCII-word and non-ASCII-word, plus `Invalid` per D3) ×
> anchored/unanchored, deduping in practice to about six distinct start states.
> Forward selects from the codepoint ending at `start`; **reverse selects from the
> codepoint beginning at `end`**. Verified load-bearing: merging the word split
> away produces 9,060 fuzz disagreements and thousands of forward/reverse
> invariant violations. Without this, `^`, `$`, `\b` and `(?m)` are wrong for any
> search not starting at offset 0 — every step of `find_iter`, and all 44 corpus
> cases carrying `bounds`.
>
> **The EOI symbol is mandatory** (`util/alphabet.rs:311`). `$`, `\z` and
> `\b`-at-end are unimplementable without it, so "one lookup per symbol" is one
> lookup per symbol plus a start-state selection plus a terminal EOI transition.
>
> **"An anchored PikeVM over that span alone" is a correctness bug if taken
> literally.** Rust narrows `Input::span` while keeping the whole haystack so
> look-around still resolves against context (`util/search.rs:150`, the
> `\bat\b` / `"batter"` example). Implemented as `List.sublist`, every boundary
> assertion at a match edge flips. The span is an index pair, never a slice.
>
> The concern that a DFA-backed `Regex` must permanently carry a PikeVM to catch
> quit errors is **void** under D3 — there is no quit set.

> **Corrected 2026-09-02 by [the D6/D11 re-measurement](../notes/2026-09-02-d6-d11-remeasure.md).**
> The amendment above overstates `starts_for_each_pattern`. Per
> `dfa/regex.rs:504-511` the **reverse DFA does not need it**, and the
> `Anchored::Pattern` call sites that do (`meta/strategy.rs:860`) are the capture
> pass — a PikeVM under D5, where per-pattern starts are free NFA start states.
> SFEP is required by the meta engine's full-DFA wrapper
> (`meta/wrappers.rs:876`), not by D5's own three-pass shape. Measured cost over
> codepoints where it *is* wanted: +2% to +17% states, with 132 start slots
> deduping to 22 distinct states at N=20.

### D6 — aho-corasick's automaton is dropped permanently

Aho-Corasick *is* a DFA over a trie with failure links standing in for
transitions a full determinization would have materialized. A folded DFA over
`foo|bar|baz` already is that automaton, denser, without the indirection. Under
D2 the subsumption is total and stays true after any future SIMD work, because
the win Teddy provides is not a better automaton.

Teddy is a different thing under the same crate name — a SIMD candidate-finder
checking 16–32 haystack positions per instruction. It is deferred behind M4's
prefilter seam, not dropped: `packed/` is 6 021 lines of which `vector.rs` (1 757)
is the portable-SIMD layer. The automaton half — `nfa/` 2 943, `dfa/` 835,
`automaton.rs` 1 608 — is dropped.

No standalone AC package. D11 carries the multi-pattern need instead.

> **1. In Roc it is slower than the engine it would accelerate.** A hand-written
> dense scalar AC measures **0.6–0.7× the codepoint DFA in every one of seven
> realistic literal sets**, at both 4 hits/KiB and 0.02. AC is the *last* rung of
> `regex-automata`'s ladder (`util/prefilter/mod.rs:630`) because the five above
> it are SIMD; Roc inherits only the bottom, and the bottom is worse than not
> prefiltering. Even in Rust, AC-as-prefilter stops paying past ~64 literals.
>
> **2. Its size win is bought at a rate D10 already rejected.** Measured in Roc:
> sparse edge-lists with failure links are **5.1× smaller per state for 9.4×
> slower** (31.8 MiB/s against 299). D10 rejected sparse tables permanently at
> 3.8× for 2.8–6.4×. Rust's better rate comes from dense-encoding the top two
> trie levels (`nfa/contiguous.rs:904`), bit-packed rows and unchecked indexing —
> **the 11.6× that falsified this decision is a Rust number the port never gets.**
> AC's *dense* form in Roc buys 4% for 2,168× the table.
>
> **3. Its three unique semantics are all out of v1** — overlapping and
> all-matches need `MatchKind::Standard`, incompatible with leftmost-first
> (`aho-corasick/src/util/search.rs:1072`), and are 77 + 74 corpus cases already
> counted out by D9's amendment; streaming needs a reader in the inner loop,
> forbidden by stop rule 4. All three are search-loop modes over an automaton D5
> and D11 already build.
>
> **Rejected: AC as the sparse engine for over-budget alternations.** 1,000
> literals determinize to 1.5 MB, folding at ~15 MB of compiler RSS under D13's
> rate — inside SR2. Raise the budget rather than carry ~5,400 lines of second
> engine.
>
> **The prefilter seam survives with two scalar rungs** (M4's remaining content):
> a lead-byte-set scan, 2.4–6.1× for ≤3 literals with rare lead bytes,
> break-even at ~10, worse than naive by 30, and a **net loss (0.68×) when the
> lead byte is ubiquitous**; and Rabin-Karp (168 lines), 1.0–1.6× and the only
> scanner that degrades gracefully. **M4 must choose not to prefilter as often as
> it chooses to**, from measured lead-byte frequency.
>
> **Reopen only if** `RegexSet` or dictionary matching enters scope, or SR6's
> throughput floor names a many-literal alternation as required. The bar is the
> 5.1×/9.4× Roc exchange rate.

### D7 — `compile` returns `Try`; the caller decides what an error means

    compile : Str -> Try(Regex, Error)

A literal pattern with a caller-side `unwrap` reaches the `crash` during folding
and **fails the build with the rendered message**. The same call with a runtime
pattern and `?` propagates an ordinary runtime `Err`. One function, one code
path, and the ahead-of-time behaviour falls out of normal Roc error handling
rather than from a language feature.

Errors are a structured tag union plus a pure renderer producing a
caret-annotated multi-line `Str`, since the crash message is a string and rich
rendering is free at compile time.

**Compilation and searching must never share a call expression.** Measured: one
runtime argument disables folding for everything inside the call, including the
parts depending only on constants. There is no partial specialization. So the
library ships no one-shot `Regex.matches(pattern, haystack)`; the idiom is
bind-then-use, now enforced by the optimizer rather than by taste.

> **Amended 2026-09-01 by [the adversarial reviews](../notes/2026-09-01-adversarial-review.md).**
> The mechanism holds and multi-line caret rendering displays readably in a build
> error. Two failures around it.
>
> **Across a package boundary, compile-time crash attribution collapses to
> `file:1:1`** — three top-level regexes, two bad, both errors pointing at the
> `app` header, distinguishable only by message content. So **every `Error`
> variant must carry the full pattern `Str` and a byte offset**, and the renderer
> must be the only supported way to produce a message. `UnclosedGroup(U64)` fails
> this.
>
> **Internal panics are uncatchable and unattributable.** An arithmetic overflow
> or a `List.get` fallback surfaces as a compile-time crash on unrelated lines of
> the user's `main!`. Roc cannot catch a crash, so the library cannot convert
> these into `Error`; the story covers only errors the library chooses to return.
>
> The stated rule — "one runtime argument disables folding for everything inside
> that call" — is **over-broad**. Measured: record fields, closures, higher-order
> arguments, `List.map`, and `Str.concat` of literals all fold. Folding is lost
> only when the pattern is threaded through a **parameter** of a call that also
> receives a runtime argument. The unguarded case is D2's own knob:
> `compile_with(lit, { max_table_bytes: runtime_budget })` silently stops folding
> with no diagnostic.

### D8 — `Iter(Span)` for iteration, `is_match` separate

`Iter` is a genuine lazy pull iterator (`Builtin.roc` 3043–3482):
`{ len_if_known, step : () -> [One({item, rest}), Skip({rest}), Done] }`, with
`Iter.custom` for building one from a seed. `find_iter` returns `Iter(Span)` and
composes with `map`/`keep_if`/`fold`/`collect`.

The block has no `any`, `find_first` or `take_while`, so early exit is
`take_first` or hand-stepping `next` — which is why `is_match` is its own
short-circuiting function rather than `find_iter |> next`.

`replace`, `replace_all` and `split` are v1.

> **Amended 2026-09-01 by [the adversarial reviews](../notes/2026-09-01-adversarial-review.md).**
> The `Iter` cost worry is **closed**: ~20 ns/match against ~5 ns for a
> hand-written loop, invisible at realistic density, and `take_first` early exit
> runs at baseline. Unverified item 5 is resolved and stop rule 4 is vindicated.
>
> The stated *reason* for a separate `is_match` is wrong — `Iter.next` is lazy and
> early exit works. The real reason is engine-level: `is_match` skips D5's reverse
> pass and the capture engine entirely.
>
> `replace`/`replace_all`/`split` are named here with nothing specified. They need
> the replacement mini-language (`$ref` with longest-possible-parse, so `$1a` is
> the group *named* `1a`; `${ref}`; `$$`), which is 536 lines in regex-lite; a
> decision on the `Str`-level return type, since `Str.from_utf8` returns a `Try`;
> and `split`'s leading/trailing empty-field semantics. **Not dispositioned.**
>
> Empty-match handling is one sentence where `util/empty.rs` is 265 lines sitting
> *below every engine* in both directions. See D15.

### D9 — Two-path corpus, differential harness early

`regex-1.13.1/testdata/` is 858 declarative cases in 23 TOML files, 6 917 lines,
in the same shape as the CommonMark JSON that already drives roc-markdown's
`SpecTest.roc`. Generate one `expect` per case.

A generated `expect` with a literal pattern exercises **only the folded path** —
it evaluates in the compiler, not in the built binary. So the suite is generated
twice: once literal, once routing the pattern through a call that also takes a
runtime argument, which forces `compile` to run in the compiled program.

The differential harness against the Rust crate is built at M1, not bolted on at
M3, so the engine's internal interfaces are shaped to make intermediate results
extractable while that is still cheap.

> **INVERTED 2026-09-01 by [the adversarial reviews](../notes/2026-09-01-adversarial-review.md).**
> This decision has the mechanism backwards. **`expect` does not fold.**
> `roc build` ignores expects entirely (248 ms whether a module holds 2 or 8);
> `roc test` executes them at runtime, serially, ~1.45 s each and ~6× slower than
> native. A bad literal pattern inside an `expect` builds clean in 170 ms and
> fails only under `roc test`.
>
> So the corpus as designed exercises the **runtime** engine, and the folded path
> — the reason the project exists — is covered by nothing. Folded verification
> must be a **program**: top-level `re_k = Regex.compile(…)` bindings asserting at
> runtime, with build time and binary size confirming the fold happened.
>
> **"858 cases" is unreachable.** Three reviewers counted independently: 160, 166,
> and 382 (44%) of cases touch a feature v1 has no function for — CRLF mode (108),
> `\b{start}`/`\b{end}` (92), overlapping (77), `match-kind = "all"` (74),
> multi-pattern (59, deferred by D11), `bounds` (44), anchored (39),
> line-terminator (11), earliest (9), match-limit (5), POSIX classes (5), `(?x)`
> (1). "What done means" must name the reachable subset with a number.

### D10 — Dense table, `U32` state ids, budget in bytes

Size is `states × byte_classes × width`. Byte-class compression is the dominant
lever and is not optional: 256 columns collapse to typically 5–40.

Dense over sparse because a sparse row needs a scan or binary search per byte,
which is bad in Rust and worse without unchecked indexing. `U32` over
build-time-selected widths because the latter costs a `[Dense8, Dense16,
Dense32]` artifact and three search loops, for a 2–4× size win that should wait
for M0's numbers to justify it.

The budget is expressed in table bytes rather than state count, so the knob means
the thing the caller cares about. Exceeding it is **not an error**: it is a
silent downgrade to the PikeVM with identical semantics.

> **Amended 2026-09-01** by [the adversarial reviews](../notes/2026-09-01-adversarial-review.md) and
> [the codepoint-alphabet studies](../notes/2026-09-01-codepoint-alphabet.md).
>
> Dense and `U32` **survive and are the right calls** — a folded `List(U32)`
> stores at exactly 4.00 bytes/element, and sparse was measured at 3.8× smaller
> for a 2.8–6.4× search cost, which is the wrong trade. But the stride is now
> D3's 3–8 codepoint classes, not 113 byte classes, so the tables are hundreds of
> bytes and `U32` is no longer a size question at all.
>
> Two corrections. Byte-class compression was claimed at 6–50×; measured on
> Unicode patterns it is **~2.3×** — moot under D3, but the number was wrong. And
> the size formula understates by up to 2× because stride rounds to the next power
> of two (`util/alphabet.rs:337`), so an alphabet of 140 pays for 256 columns.
>
> **The silent downgrade needs observability.** No field, no diagnostic, no query
> — in the one case that matters (folded) the chosen engine and the table size are
> compile-time constants. Put `engine : [Dfa({ table_bytes : U64 }), PikeVm]` on
> the compiled `Regex` and let the corpus assert it.

### D11 — Pattern IDs from the start, single-pattern API in v1

`PatternID` threads through NFA match states, per-pattern capture slots, and DFA
match states as a set. Retrofitting it touches the NFA representation, the
determinizer's match-state merging and every engine's match reporting — it is not
a layer that can be added on top.

The alternative, one alternation with each branch wrapped in a capture group,
forces the capture engine to run on every match so the DFA can never answer
alone, and threads 200 slots through the PikeVM for 200 branches.

D6 removed the other multi-pattern answer, which is what makes this worth
paying for now rather than later. The public surface stays single-pattern in v1.

> **Amended 2026-09-01 by [the adversarial reviews](../notes/2026-09-01-adversarial-review.md).
> Cost claim not dispositioned.**
>
> Pattern IDs are **part of the DFA state key** (`util/determinize/state.rs:20`)
> and therefore *prevent* state merging. Twenty trivial `key\s*=\s*(\w+)`
> patterns measured at **14.1 MB** over a byte alphabet. The retrofit argument
> stands and the NFA/PikeVM cost really is small; "small constant cost" is not
> what the DFA numbers say. The measurement predates D3's reversal and must be
> retaken over codepoints before this decision is settled.

> **RETAKEN 2026-09-02 by [the D6/D11 re-measurement](../notes/2026-09-02-d6-d11-remeasure.md).
> D11 stands, more cleanly than it argued.**
>
> **The marginal cost for v1's single-pattern API is exactly zero** — identical
> state count, identical table bytes, identical determinization time, identical
> state-key bytes, across ten patterns in three modes. Structurally so, not by
> luck: `util/determinize/state.rs:657` refuses to encode `PatternID::ZERO` when
> it is the only ID, so a single-pattern key *is* a key with no pattern-ID
> machinery. "Cheap now, expensive to retrofit" survives unconditionally.
>
> **The review's 14.1 MB was one direction over bytes, and was 99% UTF-8
> bookkeeping.** Twenty `key\s*=\s*(\w+)` patterns: 27.94 MB byte-side for both
> directions against **118.2 KB** over codepoints — 242× smaller, 30× fewer
> states, and determinization falls from **119 s to 19 ms**. N=100 is 893 KB and
> 419 ms. Growth is linear in N.
>
> **New constraint, and it is not optional: thread pattern IDs through the
> forward DFA only.** All the merging-prevention lives in the reverse
> `MatchKind::All` DFA, which does not break at first match and so accumulates
> real pattern-ID sets — 2.74× on a tokenizer set, 4.35× on a Unicode set.
> The reverse DFA never needs to know *which* pattern matched, only whether one
> did (`dfa/regex.rs:504-511`); building it without pattern IDs validated at
> **zero disagreements over 107,766 checks**. Forward-only costs **1.02–1.08×**
> across every set measured. Left unstated, an implementor mirrors the crate's
> config into both directions and pays 2.7–4.4× on exactly the tokenizer-shaped
> set a `RegexSet` exists for.
>
> Validation: 7,775 curated + 518,270 fuzz + 185,793 regression checks against
> `meta::Regex::new_many` comparing `(pattern_id, start, end)`, zero
> disagreements; the negative control (pattern IDs out of the state key) fails
> 50% of fuzz checks.

### D12 — Vertical slice, not layers

Argued at M1 above. The reason is specifically that the fold is unverified at
scale, and a vertical slice finds that out while the thing to discard is small.

> **Amended 2026-09-01 by [the adversarial reviews](../notes/2026-09-01-adversarial-review.md).**
> This is not a decision — it names no rejected alternative, unlike every other
> entry. **Eleven decisions, not twelve.**
>
> The vertical-slice *argument* survives and is strengthened: the fold is exactly
> what needed early testing, and testing it early is what produced every
> correction on this page. The *scoping* does not. M1 as written is `regex-lite`
> (measured 9,717 lines, a finished shipping engine) minus Unicode, plus pattern

### D13 — Compile-time construction rules (added 2026-09-01)

Added by [the codepoint-alphabet studies](../notes/2026-09-01-codepoint-alphabet.md) and
[the adversarial reviews](../notes/2026-09-01-adversarial-review.md). These are compiler-behaviour
facts, not style preferences, and getting them wrong is the difference between a
276-character pattern building in 1.77 s and OOM-killing the compiler.

**Never `List.concat` a growing accumulator at compile time.** It is quadratic in
compiler memory; append into the live accumulator instead. Measured on identical
output, checksum-verified: a 4,608-character pattern costs 6,232 MB by concat and
**248 MB** by append, 1.28 s against 0.42 s.

**Never `List.set` a compile-time accumulator.** It copies the whole list and
never frees — 3.8 MB retained *per call*. Back-patching a 15.5M-cell build costs
5.4–6.6 GB against 0.9 GB. The NFA emitter must write **forward-only with
precomputed subtree sizes**, never patch.

Compile-time evaluation frees nothing during a root's evaluation. With flat
construction, memory is linear at ~10 bytes of compiler RSS per artifact byte
(~7.6 storage, ~2.2 transient), plus ~30 KB per pattern character from the AST.
With flat construction, N regex constants also stop multiplying peak RSS — two
patterns went from 1.91× to 1.06× — so there is no reason to serialize folds.

### D14 — Three budgets, checked during expansion (added 2026-09-01)

Added by [the adversarial reviews](../notes/2026-09-01-adversarial-review.md); demanded independently
by both reviews and both measurement studies. D2's single `max_table_bytes` is
insufficient by construction: it caps the finished artifact, and every explosion
happens upstream of it.

`((a{100}){100}){100}` — twenty characters — is 1,020,205 NFA states and 61 s of
determinization before failing at a 4 GiB cap. Rust rejects it in **5 ms** via
limits this plan never named: `nfa_size_limit` 10 MB
(`regex-1.13.1/src/builders.rs:53`) and `nest_limit` 250
(`regex-syntax/src/ast/parse.rs:141`).

Three budgets, all returning `Err` through D7's existing `Try` — so a literal
bomb fails the build with a message and a runtime bomb returns an error:

1. **AST nest limit**, checked while parsing.
2. **NFA size limit**, checked *during* expansion, since expansion is where the
   multiplier lives.
3. **Determinizer auxiliary budget**, bounding transient allocation, not the
   finished table.

D1 admits attacker-supplied patterns, so without these the library is a remote
DoS in any program that greps user input — and because D7 folds literals, a
build-time one as well.

> **Amended 2026-09-02 by [the D6/D11 re-measurement](../notes/2026-09-02-d6-d11-remeasure.md) — a
> fourth budget, and the shape to size it against.** Multi-pattern
> determinization explodes on *N patterns that can all be live simultaneously
> over an unbounded class*, which is what a `RegexSet` gets pointed at.
> Measured, pattern-ID-independent: `[a-t][a-z]*end` × 8 is **438,701 states /
> 26.8 MB / 3.1 s**; `.*<literal>` × 8 is **2,740,293 states / 334 MB / 37 s**.
> Growth is ×5–7 per additional pattern.
>
> **A finished-artifact cap cannot see 2.7M states coming.** Budget 3 must be a
> **state-count budget checked during determinization**, not a byte cap on the
> result. Note this is a determinization problem, not a fold problem — D13's
> construction rules do not touch it.

### D15 — Empty-match semantics (added 2026-09-01)

Added by [the adversarial reviews](../notes/2026-09-01-adversarial-review.md). D4's single sentence
covers roughly a quarter of the problem and the omissions are corpus-visible.

The **iterator advance rule**: keep `last_match_end`; if a match is empty and its
end equals `last_match_end`, discard it and re-search from `start + 1`
(`util/iter.rs:433`). Without it, `compile("")` plus `find_iter` is an infinite
loop. An **empty match at end of haystack is reported** — `""` on `"abc"` gives
four matches for three bytes. **Suppression is positional, not global** — `b|` on
`"abc"` gives `[0,0],[1,2],[3,3]`, suppressing `[2,2]` but not `[3,3]`.

And the codepoint-splitting rule is **not** an iterator rule: `util/empty.rs` is
265 lines sitting *below every engine*, invoked in forward search, reverse search
and the PikeVM separately. It belongs in M1, not M2.

## Deferred, with the reason

- **Teddy / `packed/`** — needs user-facing vector types. Seam built at M4.
- **`RegexSet` public API** — the automaton supports it from M1 (D11); only the
  surface waits.
- **Unicode Tier B/C** — 25 k lines of tables for rarely-written properties.
- **One-pass DFA, bounded backtracker** — both earn their place in Rust largely
  through constants unavailable without SIMD and unsafe indexing. Revisit only
  behind a benchmark.
- **Sparse tables** — permanently, per D10.
- **`U16` state ids** — a 2× size win for about a day, once M0 says patterns land
  in the 10 k-state range.
- **Lookaround, backreferences** — excluded, as in Rust, by the linear-time
  guarantee.
- **Opaque `Regex` type** — wanted, currently crashes the compiler (probe log
  §10). Filed, not designed around; the plan assumes it works.

## What is asserted and not verified

1. **That the fold survives library scale.** All of it was measured on toys. M1
   is the test.
2. **Whether the interpreter's 1024-call-depth cap applies.** The eval README
   says compile-time roots execute as dev-backend machine code on native hosts,
   with the `LirInterpreter` used when the compiler targets wasm — so the cap may
   not apply to a native build at all. A recursive-descent parser and an NFA
   compiler both recurse on pattern structure. Unverified either way.
3. **Whether a folded table that no live code reaches is stripped.** Matters for
   Tier A tables when a program uses only ASCII patterns.
4. **Whether folded artifacts dedupe across call sites.** The probe that appeared
   to show this was invalid — the expensive work did not depend on the pattern,
   so CSE explains the result. Unmeasured.
5. **Whether `Iter`'s per-step closure allocation is acceptable** at match
   density typical of `find_iter` over a large haystack.
6. **Unicode state counts.** M0.

## Owed upstream

1. **Bug:** SIGSEGV in `postcheck/monotype/lower.zig:16175 instNodeContent` for a
   nominal type with a record payload containing a `List`. Minimal repro in
   `notes/probes/fold/varB.roc` plus `engB/`; independent of compile-time
   evaluation.
2. **Feature request, and the more valuable of the two:** specialize a call on
   its constant arguments when other arguments are runtime. This is the missing
   partial-evaluation step behind D7's restriction, and it is what would let
   one-shot APIs fold. Every library that wants to exploit compile-time
   evaluation will hit this same wall.
